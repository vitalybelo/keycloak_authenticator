# Keycloak Advanced Brute Force Protector

Кастомный плагин для Keycloak, расширяющий стандартные механизмы защиты от подбора паролей (Brute Force). Решение представляет собой комплексный контур безопасности, блокирующий злоумышленников на всех этапах аутентификации: от формы ввода пароля до генерации токенов доступа.

## 🏗 Архитектура решения (Тройная защита)

Плагин состоит из трех независимых, но тесно интегрированных компонентов (Keycloak SPI), которые обмениваются данными через распределенный кэш Infinispan.



1. **Custom Event Listener (`CustomEventListenerProvider`) — «Анализатор»**
    * Работает в фоне и прослушивает события Keycloak (в частности, `LOGIN_ERROR`).
    * Собирает статистику неудачных попыток входа и записывает таймстампы в кэш.
    * На лету вычисляет статус блокировки (`NONE`, `TEMPORARY`, `CRITICAL`) на основе сложных алгоритмов (включая всплески активности в узких временных окнах).

2. **Custom Password Authenticator — «Привратник»**
    * Встраивается непосредственно в Authentication Flow (шаг ввода пароля).
    * Перед тем как проверять валидность введенного пароля, обращается к кэшу Infinispan.
    * Если статус пользователя `TEMPORARY` или `CRITICAL` — жестко блокирует процесс входа, не позволяя Keycloak тратить ресурсы на хэширование и сверку паролей, и выдает соответствующую ошибку в UI/API.

3. **Custom Token Mapper — «Вышибала»**
    * Работает на самом низком уровне — при генерации токенов (например, Direct Naked Grant, Refresh Token).
    * Жестко блокирует любые попытки получить токен для пользователя, чей статус в кэше помечен как заблокированный.
    * Закрывает уязвимости обхода стандартных форм аутентификации через прямые запросы к Token Endpoint.

## 🚀 Ключевые особенности (Features)

* **Трехуровневая система блокировок (`BlockType`)**:
    * `NONE` — штатный режим работы.
    * `TEMPORARY` — блокировка при превышении общего лимита ошибок или обнаружении быстрых автоматизированных скриптов.
    * `CRITICAL` — жесткая блокировка при обнаружении агрессивной атаки.
* **Защита от понижения статуса (Downgrade Protection)**: Алгоритм гарантирует, что хакер не сможет сбросить критическую блокировку на временную, искусственно замедлив темп атаки.
* **Ограничение потребления памяти (Memory Leak Safe)**: История попыток лимитируется и автоматически очищается от устаревших записей в Infinispan.
* **Динамическая конфигурация (Hot Reload)**: Все параметры защиты (лимиты, окна времени) вычитываются из настроек аутентификатора в Keycloak Admin Console. Плагин можно перенастроить без перезагрузки узлов.
* **Потокобезопасность**: Использование атомарных операций (`cache.compute`) обеспечивает надежную работу при распределенных атаках в несколько потоков.

## ⚙️ Параметры конфигурации

Настройки задаются в админ-панели Keycloak для соответствующего `Authenticator` (ID: `BRUTE_FORCE_PASSWORD_FORM_ID`).

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `isSwitchedOn` | `Boolean` | Главный рубильник (true/false) для включения/выключения логики защиты. |
| `maxFailures` | `Int` | Общее количество допустимых ошибок входа до срабатывания `TEMPORARY` блокировки. |
| `blockDurationMinutes` | `Long` | Длительность `TEMPORARY` блокировки (в минутах). |
| `resetDurationMinutes` | `Long` | Широкое окно памяти (TTL). Время в минутах, через которое история ошибок полностью сбрасывается при отсутствии активности. |
| `quickLoginCheckInMillis` | `Long` | Окно в миллисекундах для детекта двух подряд идущих запросов (защита от скриптов без задержек). |
| `criticalFailuresThreshold` | `Int` | **(Параметр N)** — Порог ошибок для срабатывания жесткой `CRITICAL` блокировки. |
| `criticalTimeWindowMinutes` | `Long` | **(Параметр T)** — Узкое временное окно (в минутах), в котором анализируется всплеск ошибок для `CRITICAL` блокировки. |
| `criticalBlockInMinutes` | `Long` | Длительность `CRITICAL` блокировки (в минутах). |

## 📦 Развертывание (Deployment)

1. Соберите проект (например, `mvn clean install` или `gradle build`).
2. Скопируйте полученный `.jar` файл в директорию `providers/` вашего сервера Keycloak.
3. Убедитесь, что сервисы зарегистрированы в `META-INF/services/`:
    * `org.keycloak.events.EventListenerProviderFactory`
    * `org.keycloak.authentication.AuthenticatorFactory`
    * `org.keycloak.protocol.ProtocolMapper`
4. Выполните сборку конфигурации Keycloak (`kc.sh build`) и перезапустите сервер.
5. В Keycloak Admin Console:
    * Добавьте ваш `EventListener` в разделе *Events -> Config*.
    * Настройте `Authentication Flow`, добавив ваш кастомный аутентификатор.
    * Настройте мапперы для нужных клиентов.

   
# 📱 Telegram 2FA (Двухфакторная аутентификация через Telegram)

Встроенный комплексный механизм для использования мессенджера Telegram в качестве второго фактора аутентификации (OTP). Плагин обеспечивает бесшовный процесс привязки аккаунта и безопасную доставку одноразовых кодов.

## 🏗 Архитектура Telegram 2FA

Модуль состоит из трех ключевых компонентов (SPI), которые автоматизируют весь жизненный цикл работы со вторым фактором:

1. **Telegram Resource Provider (Webhook & API)**
   * Регистрирует кастомные REST-эндпоинты в Keycloak.
   * **`/webhook`**: Слушает входящие PUSH-уведомления от серверов Telegram. Ловит команды `/start {token}` и асинхронно сохраняет `chat_id` пользователя во временный кэш Infinispan.
   * **`/status/{token}`**: Эндпоинт для фронтенда, позволяющий реализовать polling (опрос статуса). Как только Webhook получает `chat_id`, фронтенд узнает об этом и автоматически сабмитит форму привязки.

2. **Telegram Bind Required Action — «Процесс привязки»**
   * Если у пользователя не найден атрибут с `chat_id` Telegram, система автоматически перехватывает поток и перенаправляет пользователя на экран привязки (Required Action).
   * Генерирует уникальный UUID-токен, который вшивается в ссылку на Telegram-бота.
   * После успешного получения `chat_id` через Webhook, провайдер извлекает его из кэша Infinispan и навсегда сохраняет в атрибутах пользователя Keycloak.

3. **Telegram Authenticator — «Генератор OTP»**
   * Встраивается в Authentication Flow.
   * Генерирует одноразовый числовой код (OTP) и отправляет его пользователю напрямую в Telegram через Telegram Bot API (`sendMessage`).
   * Контролирует срок действия кода (TTL). Если время вышло, старый код инвалидируется, автоматически генерируется новый и отправляется в чат, а пользователю выводится соответствующее уведомление.

## ⚙️ Параметры конфигурации Telegram 2FA

Настройки задаются в админ-панели Keycloak для аутентификатора `Telegram 2FA` (ID: `telegram-authenticator`).

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `Telegram 2FA switch` | `Boolean` | Включение или выключение логики запроса второго фактора через Telegram. |
| `Code TTL (seconds)` | `Int` | Время жизни одноразового кода в секундах. По истечении этого времени код будет отвергнут в методе `action()`. |
| `Code length` | `Int` | Количество цифр во временном коде (длина генерируемого OTP). |

## 🔒 Безопасность и отказоустойчивость
* **Infinispan Cache:** Использование `InfinispanConnectionProvider` для передачи данных между Webhook-контроллером и Required Action гарантирует корректную работу даже в кластерной (многоузловой) конфигурации Keycloak.
* **Изолированное состояние:** Секретные коды и время их генерации хранятся строго в заметках сессии аутентификации (`AuthNotes`) и уничтожаются сразу после успешного ввода.


# 🚀 Настройка Webhook для локальной разработки

Чтобы Telegram-бот мог отправлять входящие сообщения на ваш локальный сервер Keycloak, необходимо создать публичный туннель с помощью утилиты `ngrok`.

### Шаг 1: Запустите локальный Keycloak
Убедитесь, что ваш сервер Keycloak запущен и слушает нужный порт (например, `8443` или `8080`).

### Шаг 2: Пробросьте порт через ngrok
Откройте новый терминал и выполните команду для проброса порта (укажите порт вашего Keycloak):
`bash
ngrok http 8443
`

### Шаг 3: Получите публичный адрес
После запуска ngrok в консоли появится статусная информация. Найдите строку `Forwarding` и скопируйте сгенерированный HTTPS-адрес:
`text
Forwarding  https://a1b2-c3-d4.ngrok-free.app -> http://localhost:8443
`

### Шаг 4: Зарегистрируйте Webhook в Telegram
Теперь нужно сообщить Telegram-боту ваш новый публичный адрес. Для этого выполните `curl`-запрос в терминале, подставив свой актуальный домен от ngrok в параметр `url` и указав токен вашего бота:

`bash
curl -F "url=https://georgiana-lawny-stephany.ngrok-free.dev/realms/SpringBootKeycloak/telegram/webhook" \
     https://api.telegram.org/bot8719040842:AAFiZKnA0ts82CARQNs2_lWM_DpKt5da0m0/setWebhook
`

> **Важно:** > * В примере выше URL `https://georgiana-lawny-stephany.ngrok-free.dev` нужно заменить на ваш текущий адрес из Шага 3.
> * Если вы используете бесплатную версию ngrok, при каждом перезапуске утилиты публичный домен может меняться. В этом случае **Шаг 4** нужно будет выполнить заново.
> * *Примечание по безопасности:* Для production-среды никогда не публикуйте токен бота в открытых репозиториях.

## ⚙️ Настройка в панели администратора Keycloak
1. Перейдите в раздел **Authentication**.
2. Создайте новый флоу (или скопируйте Browser flow).
3. Добавьте исполнение **Telegram Authenticator** и настройте его как `REQUIRED` или `ALTERNATIVE` в зависимости от вашей логики.
4. В разделе **Required Actions** убедитесь, что действие **Telegram Required Action** включено.

# 🔀 Attribute Conditional (Условное выполнение потока по атрибутам)

Кастомный условный аутентификатор (`ConditionalAuthenticator`), который позволяет динамически управлять выполнением шагов (Executions) внутри Authentication Flow. Плагин проверяет наличие заданных атрибутов и их значений у пользователя или групп, в которых он состоит, и на основе этого принимает решение: пропускать поток дальше или игнорировать данный шаг.

## 🏗 Как работает Attribute Conditional

Провайдер (`check_attribute_condition`) интегрируется в Keycloak как узел условия (Condition).

1. **Проверка пользователя:** При попадании на шаг условия, плагин считывает конфигурацию и проверяет наличие указанного атрибута (`Attribute name`) в профиле пользователя.
2. **Сверка значений:** Если атрибут найден, его значение сверяется со списком разрешенных значений (`Attribute value list`).
3. **Проверка групп (Опционально):** Если включен флаг проверки групп, плагин дополнительно обходит все группы, назначенные пользователю (`user.groupsStream`), и ищет требуемый атрибут там.
4. **Инверсия логики (Native Output):** Плагин поддерживает негативные сценарии. Если включен флаг `Native output`, логика инвертируется: шаг будет выполнен только если требуемый атрибут **НЕ** найден (или его значение не совпадает).

## ⚙️ Параметры конфигурации Conditional Authenticator

Настройки задаются в админ-панели Keycloak для узла условия `Condition - check user attribute`.

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `Attribute name` | `String` | Название атрибута, для которого проводится проверка. |
| `Attribute value list` | `Multivalued String` | Список допустимых значений атрибута, при совпадении с которыми условие будет считаться выполненным. Под капотом значения парсятся с разделителем `##`. |
| `Include groups attributes` | `Boolean` | Если установлено в `ON`, плагин будет искать совпадения атрибутов не только в профиле пользователя, но и в атрибутах привязанных к нему групп. |
| `Native output` | `Boolean` | Инверсия результата проверок. Если установлено в `ON`, условие вернет `true` (разрешит выполнение) только в случае **несовпадения** (атрибут не найден или значение не подходит). |

## 💡 Примеры использования в Flow
* **Двухфакторка только для сотрудников:** Настроить вызов `Telegram 2FA` только если атрибут `user_type` равен `employee`.
* **Обход защиты:** Пропускать шаг `Brute Force Protector` для сервисных учетных записей (проверка по атрибуту в группе `service_accounts`).
* **Ограничение доступа:** Блокировать вход (через вызов Deny Access), если у пользователя найден атрибут `migration_status` со значением `pending` (используя инверсию `Native output`).


# ⏳ Enter Time Logics (Контроль неактивности и принудительная смена пароля)

Кастомный аутентификатор (`Enter Time Attribute Logic`), который отслеживает время последнего входа пользователя в систему. Если пользователь не авторизовывался дольше разрешенного периода, плагин автоматически назначает ему требование обязательной смены пароля.

## 🏗 Как работает Enter Time Logics

Провайдер (`enter_timer_logics`) встраивается в Authentication Flow и работает "под капотом", не прерывая сам процесс проверки учетных данных.

1. **Проверка неактивности:** Если логика проверок включена, плагин считывает время предыдущего входа из атрибутов пользователя и вычисляет разницу с текущим временем.
2. **Назначение Required Action:** Если период отсутствия превышает установленный в настройках лимит (в днях), плагин автоматически вешает на пользователя обязательное действие `UserModel.RequiredAction.UPDATE_PASSWORD`. После успешной аутентификации Keycloak сам перенаправит пользователя на форму обновления пароля.
3. **Регистрация входа (Аналитика):** Вне зависимости от того, включена проверка периода или нет, плагин **всегда** обновляет атрибут пользователя, записывая в него текущее время в ISO-формате при каждом успешном прохождении узла. Это позволяет использовать плагин просто как логгер активности.

## ⚙️ Параметры конфигурации Enter Time Logics

Настройки задаются в админ-панели Keycloak для узла `Enter Time Attribute Logic`.

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `Enter time switch` | `Boolean` | Главный рубильник (true/false). Если установлено в `ON`, плагин будет сверять время и требовать смену пароля. Если `OFF` — плагин будет только тихо обновлять атрибут времени последнего входа. |
| `Period in days to force change password` | `Int` | Количество дней неактивности (по умолчанию 30). Если пользователь не входил в приложение дольше этого времени, сработает триггер обновления пароля. |

## 💡 Особенности реализации
* Расчет времени производится с точностью до миллисекунд с использованием `java.time.ZonedDateTime` и `Duration`.
* В логах сервера фиксируется подробная статистика неактивности пользователя (в днях, часах, минутах и секундах).


# 🛑 Username Login Limiter (Ручная блокировка по логину)

Кастомный аутентификатор (`Username Login Limiter`), который выполняет роль жесткого фильтра на этапе входа. Он позволяет администратору вручную задать список логинов (`username`), которым будет категорически запрещен доступ к системе, независимо от правильности введенного пароля или прохождения других проверок.

## 🏗 Как работает Username Limiter

Провайдер (`username_blocking_execution`) встраивается в поток аутентификации и перехватывает логин текущего пользователя.

1. **Нормализация данных:** Плагин считывает список заблокированных имен из настроек и приводит их, а также логин текущего пользователя, к нижнему регистру (`lowercase()`). Это защищает от банальных попыток обойти блокировку изменением регистра букв (например, ввод `Admin` вместо заблокированного `admin`).
2. **Учет типа выполнения (Requirement):**
   * Если шаг аутентификатора настроен как `REQUIRED`, и пользователь находится в "черном списке", плагин немедленно прерывает поток с ошибкой `INVALID_USER` и отображает страницу с сообщением: *"User login \"{username}\" blocked by administrator"*.
   * Если шаг настроен как `ALTERNATIVE` или `CONDITIONAL`, плагин мягко помечает попытку как `attempted()`, позволяя механизмам Keycloak переключиться на альтернативные ветки аутентификации.
3. **Пропуск валидных пользователей:** Если логина нет в списке или общая блокировка выключена, пользователь беспрепятственно проходит на следующий шаг (`context.success()`).

## ⚙️ Параметры конфигурации Username Limiter

Настройки задаются в админ-панели Keycloak для узла `Username Login Limiter`.

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `Blocking switch` | `Boolean` | Главный рубильник плагина. Если установлено в `ON`, выполняется проверка по `username`. Если `OFF` — плагин деактивируется и пропускает всех. |
| `Blocking username list` | `Multivalued String` | Список логинов пользователей, которым запрещен вход. Под капотом введенные значения парсятся с использованием разделителя `##`. |

## 💡 Сценарии использования
* **Изоляция:** Быстрое изолирование скомпрометированных учеток без необходимости удалять их профиль из базы данных Keycloak.
* **Stop-листы:** Создание временных "стоп-листов" администраторами при расследовании инцидентов безопасности.
* **Технические работы:** Блокировка доступа для конкретных системных аккаунтов на время проведения регламентных работ.


# 💬 SMS 2FA Authentication (Демонстрационный OTP-аутентификатор)

Кастомный аутентификатор (`2FA SMS Authentication`), реализующий логику второго фактора (2FA) через одноразовые пароли по СМС. Данный плагин разработан в демонстрационных и отладочных целях: физическая отправка СМС не производится, а для удобства тестирования предусмотрен вывод сгенерированных кодов в лог и поддержка режима "заглушки" (stub).

## 🏗 Как работает SMS 2FA

Провайдер (`sms_2fa_authentication`) встраивается в Authentication Flow как шаг проверки второго фактора.

1. **Проверка профиля:** Шаг считается актуальным и активируется только в том случае, если у пользователя заполнен профильный атрибут `phone`.
2. **Генерация кода:** В зависимости от конфигурации, плагин либо генерирует безопасный случайный цифровой код заданной длины, либо использует статичный фиктивный код (в режиме stub).
3. **Симуляция отправки (Debug mode):** В коде специально оставлен блок `TODO` для интеграции с реальным SMS-провайдером. На этапе отладки плагин просто выводит сгенерированный секретный код в консоль/лог сервера (`>>>> Created SMS secret code = ...`), чтобы разработчик мог его скопировать.
4. **Валидация и TTL:** Введенный на форме код строго сверяется с тем, что был сохранен в защищенных заметках сессии (`AuthNotes`). Если время жизни кода (TTL) истекло до момента ввода, плагин признает его недействительным и предлагает пользователю повторить попытку.

## ⚙️ Параметры конфигурации SMS 2FA

Настройки задаются в админ-панели Keycloak для узла `2FA SMS Authentication`.

| Параметр | Тип | Описание |
| :--- | :--- | :--- |
| `Use stub switch` | `Boolean` | Режим симуляции. Если установлено в `ON`, система не генерирует случайные пароли, а всегда ожидает ввода фиктивного СМС-кода (удобно для сквозного тестирования). |
| `Dummy sms stub code length` | `Int` | Количество знаков генерируемого секретного кода (используется, если режим stub выключен). |
| `Dummy sms stub code value` | `String` | Статичное значение фиктивного СМС-кода для прохождения успешной 2FA (по умолчанию `1111`). |
| `Timeout waiting for SMS code value` | `Int` | Значение тайм-аута (TTL) в секундах, в течение которого код считается действительным. |

## 💡 Особенности реализации
* Все параметры, включая сам код и срок его действия, безопасно передаются между этапами аутентификации через `context.authenticationSession.setAuthNote(...)`, что исключает их перехват на клиентской стороне.
* В случае внутренних ошибок или проблем с "отправкой", пользователю возвращается корректная страница `INTERNAL_SERVER_ERROR` с пояснением.


# Keycloak Trusted Device SPI

Кастомное расширение (SPI) для Keycloak, реализующее механизм «Доверенных устройств» (Trusted Device / Remember Me). Плагин позволяет пользователям безопасно пропускать шаг двухфакторной аутентификации (2FA) на устройствах, которые они ранее явно отметили как доверенные.

## 🚀 Возможности (Features)

* **Обход 2FA:** Автоматический пропуск второго фактора при наличии валидной подписанной cookie.
* **Криптографическая защита:** Идентификатор устройства (`fingerprint`) упаковывается в JWT и подписывается активным RS256 ключом реалма (Realm Active Key).
* **Self-Service:** Пользователи могут просматривать и удалять свои доверенные устройства прямо из стандартного интерфейса управления аккаунтом (Account Console).
* **Гибкая настройка:** Все параметры (включение/выключение, TTL, режим восстановления) вынесены в графическую административную панель Keycloak.
* **Отказоустойчивость:** Встроенный механизм автоматического восстановления удаленных учетных данных (`credential`) при предъявлении валидной криптографической cookie.

## 🛠 Архитектура и компоненты

Решение состоит из трех основных независимых модулей:

### 1. Trusted Device Checker (`trusted-device-authenticator`)
Аутентификатор, проверяющий наличие и валидность cookie перед запросом 2FA.
* Извлекает персонализированную cookie (вида `AUTH_TRUSTED_DEVICE_{userId}`) и верифицирует JWS-подпись.
* Сверяет извлеченный `fingerprint` с записями в таблице `credentials` пользователя.
* Если устройство найдено и валидно — аутентификация успешно продолжается без отображения формы OTP.

### 2. Remember Device Form (`remember-device-authenticator`)
Аутентификатор, предлагающий пользователю запомнить устройство.
* При отсутствии cookie отображает Freemarker-шаблон `remember-device.ftl`.
* При согласии генерирует уникальный UUID (`fingerprint`), сохраняет его в БД и формирует JWT-токен.
* Устанавливает `HttpOnly`, `Secure` cookie с настроенным временем жизни (TTL).

### 3. Trusted Device Credential Provider (`trusted-device`)
Провайдер для хранения связок устройств в БД Keycloak.
* Сохраняет `fingerprint` в формате JSON в поле `secretData`.
* Имя устройства для отображения в личном кабинете обрезается и генерируется на основе HTTP-заголовка `User-Agent` браузера.

## ⚙️ Настройка Authentication Flow в Keycloak

Для корректной работы плагина необходимо модифицировать стандартный поток аутентификации (Browser Flow) или создать его копию.

### Интеграция Trusted Device Checker
Добавьте этот шаг в поток **перед** формой запроса OTP/2FA.
* **Requirement:** `Alternative` (Альтернативный).
* **Поведение:** Если чекер отрабатывает успешно, форма OTP пропускается. Если нет — управление передается следующему шагу (стандартному OTP Form).

### Интеграция Remember Device Form
Добавьте этот шаг в поток **после** успешного прохождения OTP/2FA.
* **Requirement:** `Required` или `Alternative` (в зависимости от вашей архитектуры потока).
* **Поведение:** Если у пользователя еще нет cookie, ему будет показана форма с чекбоксом `rememberDevice`.

## 🎛 Конфигурация провайдеров (Admin Console)

Оба аутентификатора поддерживают глубокую настройку через меню **"Actions -> Config"** в настройках Flow.

**Настройки Trusted Device Checker:**
* **Trusted device enabled:** Если "ON" - будет выполняться проверка наличия fingerprint доверенного устройства в cookies и credentials, аутентификатор вернет успех если они совпадают.
* **Hard delete enabled:** Если "ON" - принудительно будут удаляться все fingerprints из cookie при входе пользователя, credentials сохранятся.

**Настройки Remember Device Form:**
* **Remember device enabled:** Если "ON" - будет выполняться сохранение fingerprint для доверенного устройства в cookie и credential.
* **Cookie TTL (days):** Время жизни fingerprint доверенного устройства, после чего он автоматически удаляется из cookie.
* **Recovery credential enabled:** Если "ON" - будет выполняться восстановление fingerprint в credential пользователя, если при прохождении потока обнаружено, что fingerprint существует в cookie, но из учетных данных был вручную удален.
